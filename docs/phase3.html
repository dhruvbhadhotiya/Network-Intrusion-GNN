Graph Construction

Transforming the tabular network flow data into a heterogeneous IP-to-IP directed graph for PyTorch Geometric. Each unique IP address becomes a node; each network flow becomes a directed edge. The task is edge classification — predict whether each flow is normal or an attack.

🏗️ Graph Design

Nodes — IP Addresses

Every unique IP address in the training set is mapped to a node index 0–49. Any IP not seen in training is mapped to a single shared UNK node (index 50). This handles unseen IPs at inference time without graph structure changes.

Node features (11 dimensions) are computed per IP from the training set: out-degree, in-degree, out-bytes (mean), in-bytes (mean), attack ratio, protocol entropy, service entropy, mean TTL (src), mean TTL (dst), mean duration, and connection rate. These aggregate the historical traffic profile of each endpoint.

Edges — Network Flows

Each network flow record becomes a directed edge from srcip node to dstip node. Multi-edges are preserved (same IP pair can have many flows).

Edge features (37 dimensions) are exactly the 37 preprocessed flow features from Phase 2 — all normalised and encoded. This is the primary signal used for classification. The edge label is the 10-class attack category (or Normal), reduced to binary for the binary task.

Why edge classification? Unlike node classification (where each node has one label), here each individual network flow carries its own label. This naturally maps to edge classification: we classify each directed edge (srcip → dstip) using both the edge's 37 flow features and the learned node embeddings of its endpoint IPs. GNNs add value by allowing a flow's classification to be influenced by the overall traffic pattern of the source and destination IPs.

⚠️ Test set graph is fundamentally different from train/val. The test split has only 1 unique src→dst pair and 51 weakly connected components — meaning every test flow connects to the UNK node (index 50). No real node-level neighbourhood structure exists on the test graph. GNNs that rely heavily on neighbourhood aggregation will fail to leverage their key advantage on this split, which explains the severe val→test performance drop in Phase 5.

📈 Graph Structure Visualisations

Node Degree Distribution
Log-scale histogram of in-degree and out-degree across 51 nodes. The distribution is highly skewed — a small number of server IPs (e.g., DNS servers, HTTP servers) have extremely high in-degree (receiving from many sources), while most client IPs have moderate degree. This power-law-like distribution is characteristic of real internet traffic graphs. The maximum out-degree of 154,082 edges belongs to the most active client IP in the training set. High-degree nodes will have strong learned embeddings; low-degree nodes (and UNK) will have weaker representations.
Edge Label Distribution (Train / Val / Test)
Grouped bar chart showing the count of each of the 10 edge label classes across train, validation, and test splits. Key observation: The class proportions in train and val are nearly identical (4.84% attack each), but the test set has a completely different profile — 55.06% attack. Within attack classes, Generic and Exploits dominate in train/val, while the test set has a different per-class distribution. This reinforces the challenge: models must generalise across both the class-level shift and the graph-structural shift (UNK node).

❓ The UNK Node Problem

What is the UNK node? Node index 50 is a synthetic node representing all IP addresses not seen during training. Because the test set uses different IP subnets from train/val (the test captures occurred on different network segments), all test flows map to srcip=UNK or dstip=UNK.
ScenarioTrain / ValTest
Node neighbourhood available? Yes — 50 known IPs, 311 unique pairs No — all flows → UNK node
GNN can aggregate neighbours? Yes — meaningful IP history UNK has no meaningful embedding
Edge features still available? Yes Yes
Model type advantage GNNs ≈ baselines Baselines >> GNNs (edge features only)

This is an inductive GNN problem — the model must generalise to nodes not seen at training time. The current architecture (full-batch transductive training) does not handle this gracefully. Future work should explore inductive methods such as GraphSAINT, SEAL, or edge-only models that bypass node embeddings entirely for test flows.

🔑 Phase 3 — Key Findings

  • Tiny node set (51 IPs) but massive edge set (1.6M train edges) — this is an edge-heavy, node-sparse graph, unusual for GNNs typically designed for node-sparse, edge-dense problems in the opposite ratio.
  • Power-law degree distribution — a few gateway/server IPs dominate with 100k+ edges. GNN pooling will be dominated by these high-degree nodes.
  • Test graph is structurally disconnected — 51 weakly connected components, 1 unique pair, all connecting to UNK. This is the root cause of GNN test failure.
  • Node features aggregate IP history from training only — the UNK node's features are the mean of all known-IP features, which is a weak approximation for genuinely novel endpoints.
  • All 37 edge features preserved as PyG edge_attr — classical baselines and GNNs use the same information, ensuring a fair comparison.
